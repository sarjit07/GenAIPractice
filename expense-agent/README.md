# expense-agent

An open-source, local-only pipeline that turns an Axis Bank statement CSV into
the same kind of enriched, self-contained HTML spending report as the
`/expense-tracker` Claude Code command in the parent repo — but orchestrated as
a [LangGraph](https://github.com/langchain-ai/langgraph) graph calling a local
[vLLM](https://github.com/vllm-project/vllm) server instead of Claude doing it
agentically. No Anthropic/Claude API involved anywhere in this pipeline.

## How it works

Ten-node graph: parse the CSV → apply ordered keyword rules → send only the
genuinely ambiguous merchant fragments to a local LLM (with a JSON-schema
grammar constraint, cached by merchant so repeat runs rarely call the model at
all) → compute every number deterministically → **assert the statement
reconciles** (halt, don't render, if it doesn't) → render the HTML → **grep it
for leaked identifiers** (halt, don't write, if anything's found) → write the
file. See `expense_agent/graph.py` for the full node/edge wiring — it's meant
to be read top to bottom.

The LLM's only job is classifying short merchant-name fragments (never
amounts, dates, or account data) into a fixed category enum. No arithmetic and
no HTML is ever generated by the model.

## Setup — two processes

vLLM serving and this client run in **separate Python environments** on
purpose — the client here has no `vllm`/`torch` dependency at all, it only
speaks HTTP to whatever OpenAI-compatible server you point it at.

**Terminal 1 — the vLLM server** (uses the existing `~/.venv-vllm-metal` env
from `llm_utils/`, since vLLM has no native Apple Silicon support and that env
already has the `vllm-metal` plugin installed):

```bash
source ~/.venv-vllm-metal/bin/activate   # or whichever venv has vllm + the vllm-metal plugin
vllm serve /path/to/llm_utils/models/<model-dir> \
  --served-model-name expense-cat \
  --port 8000 \
  --max-model-len 4096 \
  --structured-outputs-config.backend xgrammar
```

The `--structured-outputs-config.backend xgrammar` flag is not optional on the
vLLM build this was verified against (0.25.1 + vllm-metal): the default
`auto` backend silently no-ops on structured output — the model produces
plain unconstrained text and `llm_client.py`'s schema validation then rejects
every response, degrading everything to `Uncategorized`/`low`. Confirmed with
a direct curl test (forcing a made-up nonsense enum and checking whether the
output was actually constrained to it) before concluding it wasn't a client
bug. `scripts/smoketest_vllm.py` will catch this if you see it again — if the
guided call comes back with `reason` containing "LLM call failed", check the
backend flag first.

Which model to serve — see **Model choice** below.

**Terminal 2 — this client** (its own lightweight venv):

```bash
cd expense-agent
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # adjust if you changed --served-model-name or the port

python scripts/smoketest_vllm.py       # confirm the server + guided decoding work
python cli.py ../data/expense-csvs/statement.csv --holder-name "Your Name"
```

Report is written to `outputs/statement-report.html` by default (`--output` to
change it). Run with `--no-llm` to exercise the whole pipeline with zero
network calls — every ambiguous transaction falls back to a deterministic
rule-based guess instead, which is enough to test parsing, reconciliation, and
rendering without a server running at all.

## Correcting a miscategorized transaction

If the rules or the LLM got a merchant wrong, correct it permanently instead
of editing the report by hand:

```bash
python scripts/correct.py "Blinkit" "Shopping"                  # apply a correction
python scripts/correct.py "Blinkit" "Shopping" --reason "..."   # with a note for yourself
python scripts/correct.py --list                                # see every correction applied
python scripts/correct.py --remove "Blinkit"                    # revert to automatic classification
python cli.py ../data/expense-csvs/statement.csv --holder-name "Your Name"  # regenerate
```

The fragment to correct is the text after "· " in the report's Description
column (`"UPI · Blinkit"` → `Blinkit`). A correction is **per-merchant, not
per-transaction** — it applies to every transaction with that exact fragment,
past and future statements alike, and takes precedence over both the keyword
rules and the LLM unconditionally. It's an exact match, not fuzzy: `"Blinkit"`
and `"BLINKIT COMMERCE PRIV"` are different fragments (different UPI
merchant-ID strings on Blinkit's end) and need separate corrections if both
appear. Corrections live in the same file as the LLM cache
(`.cache/merchant_categories.json`, gitignored) with `"source": "manual"` —
implemented in `rules.apply_manual_override()`, checked first in
`graph.rule_categorize_node()`, before any keyword rule runs.

## Model choice

Only one model is downloaded so far: `TinyLlama-1.1B-Chat-v1.0` in
`llm_utils/models/`. It's fine for **wiring/testing** the graph — the graph's
correctness (rule ordering, reconciliation, caching, rendering) doesn't depend
on classification quality, only the review-panel content does. It is **not**
recommended for real categorization runs: grammar-constrained decoding
guarantees valid JSON shape, not correct content, and a 1.1B model is a weak
instruction-follower on a 12-way classification task.

**Recommended for real use:** `Qwen/Qwen2.5-3B-Instruct` — openly downloadable
(Apache 2.0, no gated-license friction unlike Llama 3.2), strong
instruction-following at this size, ~6GB in bf16, cheap to run locally via
`vllm-metal`. Since the merchant cache keeps LLM calls near-zero after the
first run or two, the larger model's cost is paid once per unique merchant,
not per transaction — the latency difference in practice is negligible.

```bash
source ~/.venv-vllm-metal/bin/activate
python ../llm_utils/download_huggingface_model.py Qwen/Qwen2.5-3B-Instruct  # or however you fetch models today
```

## Why this design

- **No arithmetic or HTML from the LLM.** Everything in `metrics.py` and the
  chart code in `assets/report_template.html` is deterministic; the model only
  ever sees a merchant-name fragment and returns a category + confidence.
- **Reconciliation is a hard gate**
  (`opening − debits + credits == closing`, category totals sum to debits) in
  `metrics.reconcile()` — if it fails, the graph routes to `halt`, not
  `render`. This is the single most valuable check in the pipeline: it catches
  dropped rows, the "empty amount cell is a space, not an empty string"
  parsing bug, duplicates, and sign errors.
- **Verification is also a hard gate.** `verify.verify_html()` greps the
  rendered HTML for 8+ digit runs, IFSC-shaped tokens, and external
  `src`/`href` references before the file is written to disk at all — a
  verification failure is treated exactly like a reconciliation failure.
- **Colour follows the entity, assigned once**, and the donut's arc order
  follows a fixed palette-slot order rather than amount order — this repo has
  no access to the `dataviz` skill's palette validator, so the hex values in
  `config.py` are copied verbatim from a report that already passed it, rather
  than re-derived.
- **The LLM only sees the ambiguous minority.** Bare person-to-person
  transfers are never queued for the model at all — no model can infer intent
  from a human name, so they're deterministically low-confidence and go
  straight to the review panel.

## Verifying it works

No automated test suite — verify by running it. Against the real statement in
`--no-llm` mode (no server needed, deterministic rule-based fallback only):

```bash
python cli.py ../data/expense-csvs/statement.csv --holder-name "Your Name" --no-llm
```

Check the console summary for: reconciliation didn't halt the run, the balance
line matches the statement's own opening/closing figures, and the category
totals look sane. Then open `outputs/statement-report.html` in a browser,
light and dark mode, and check for clipped labels or overflow — that's the
real layout check; it's deliberately not automated (no Playwright/Selenium
dependency, keep the pipeline lean).

## Confidentiality

Same rules as the parent repo's `/expense-tracker` command: account number,
customer ID, card number, IFSC, UPI/IMPS reference numbers, and ACH mandate
IDs are masked to their last 4 characters at parse time (`masking.py`), before
anything else touches the data. Counterparty *names* are kept — the report
needs them. `.cache/` (the merchant-name cache) and `outputs/` are gitignored;
never commit either.
